# 버그 정리

**버그 위치**: `docs/bugs/BUG-NNNN-<요약>.md` (한 버그 한 파일, 팀 공유용으로 커밋)
**정리 보고서**: `docs/bugs/triage-[YYYY-MM-DD].md`

## 1. 모드
- `new` → 새 버그 보고서 작성. `bug-report-template.md` (이 스킬 폴더) 양식으로, 다음 번호를 매겨 `docs/bugs/` 에 저장할지 묻는다. 관련 파일은 코드 검색으로 채운다. 끝.
- `full` (기본) → 모든 열린 버그 분류 + 추세
- `trend` → 추세만 (읽기 전용, 본문 안 읽음)

## 2. 버그 읽기
- `docs/bugs/BUG-*.md` 를 찾는다. 없으면 "정리할 버그가 없습니다" 하고 끝.
- `trend` 모드는 머리 칸만 Grep:
  `Grep pattern="\*\*(심각도|우선순위|상태|시스템|분류|보고일)\*\*" glob="docs/bugs/BUG-*.md" output_mode="content"`
- `full` 모드는 열린(`상태: 열림`) 버그 본문을 읽는다.

## 3. 분류

### 심각도 (영향 — 객관적)
| 심각도 | 정의 |
|--------|------|
| **S1 치명** | 크래시, 진행 불가(소프트락), 데이터 손실, 기능 전체 고장 |
| **S2 높음** | 주요 기능 고장이지만 플레이는 가능. 규칙과 다른 계산 (예: 피해 공식 오류) |
| **S3 중간** | 우회 방법이 있음. 작은 오동작 |
| **S4 낮음** | 화면 깨짐, 오타. 게임플레이 영향 없음 |

### 우선순위 (급한 정도 — 팀이 정함)
| 우선순위 | 정의 |
|---------|------|
| **P1 다음 작업 전에** | 지금 작업·테스트를 막음, 또는 최근 커밋에서 생긴 회귀 |
| **P2 곧** | 다음 마일스톤(예: 1층 완성) 전에 |
| **P3 나중에** | 막는 건 없음 |
| **P4 안 고침** | 감수하거나 범위 밖 — **사용자 승인 필요** |

심각도·우선순위는 제안일 뿐, 우선순위는 팀이 정한다.

### 몰림 확인
- 같은 시스템(battle / cards / statuses / ui / 의뢰 …)에 열린 버그 3개 이상 → "이 시스템 설계·구현 점검 필요"
- 이미 완료로 기록된 기능(`docs/progress.md`)에서 난 버그 → **회귀**. 해당 GUT 테스트가 왜 못 잡았는지 함께 표시

## 4. 추세
- 열린 버그 수, 최근 정리 이후 새로 열림/닫힘
- 버그가 가장 많은 시스템, S1/S2 비율이 가장 높은 시스템
- 회귀 수
- 오래된 S1/S2 (2주 넘게 열림)

## 5. 보고서
```markdown
# 버그 정리 보고서
> 날짜: [YYYY-MM-DD] · 모드: [full|trend] · 처리한 열린 버그: [N]

## 요약
| 우선순위 | 수 | 메모 |
|---------|----|------|
| P1 | | |
| P2 | | |
| P3 | | |
| P4 후보 | | 승인 대기 |

**S1/S2 미해결**: [N]

## P1 — 다음 작업 전에
| ID | 시스템 | 심각도 | 요약 | 관련 파일 |
|----|--------|--------|------|----------|

## P2 — 곧
| ID | 시스템 | 심각도 | 요약 |
|----|--------|--------|------|

## P3 / P4
| ID | 시스템 | 심각도 | 요약 | 처리 |
|----|--------|--------|------|------|

## 구조적 문제
[몰림·회귀, 없으면 "없음"]

## 추세
[위 4번 내용]

## 권장 행동
1. [보통 "P1 부터 superpowers:systematic-debugging 으로"]
2.
```

## 6. 저장
- P4 후보가 있으면 먼저 "안 고침으로 둬도 될까요?" 묻고, 답 전까지 `P4 후보` 로 둔다.
- "`docs/bugs/triage-[날짜].md` 에 저장할까요?" 승인 후에만 쓴다.
- 각 버그 파일의 우선순위 칸을 갱신할지도 함께 묻는다.

## 원칙
- 승인 없이 버그를 닫거나 안 고침으로 두지 않는다.
- 추세는 참고용 — 그것만으로 작업을 막지 않는다.
- 버그를 고치는 건 이 스킬의 일이 아니다. 고칠 땐 superpowers:systematic-debugging 먼저.
